# 발주콕 작업 영역

서비스 흐름을 기준으로 Issue를 분리하기 위한 초안이다. 기능 범위와 API 계약의 정본은 Notion 기능명세서와 API 명세서이며, 구현 전에 해당 명세를 확인한다. 아래 영역은 작업 분류이며 별도 서비스나 폴더 구조를 의미하지 않는다.

## 영역별 책임

| 영역 라벨 제안 | 작업 범위 예시 |
| --- | --- |
| `area:foundation` | 회사, 사용자, 역할, 초대와 인증 |
| `area:master-data` | 부품·규격·카테고리, 엑셀 초기 이관, 중복 후보 확인, 설비·정비 일정·공급사 |
| `area:inventory` | 입출고 이벤트, 재고 계산, 장부 검증·실사·정정, 입고 및 실제 납기 기록 |
| `area:decision-engine` | 재주문점·소진 예상일 계산, 외부 지표 반영, 발주 초안과 검토·판정 |
| `area:approval` | 발주 승인·수정·반려, 발주 기록, PDF와 공급사 전달 문구 |
| `area:notification` | 긴급 알림, 아침 브리핑, 실사 요청과 처리 결과 알림 |
| `area:ai` | 채팅 해석, 검토 의견서 문장, 엑셀 이관 규격·카테고리 제안, 부품 이름 임베딩 |
| `area:contracts` | server와 ai 사이의 요청·응답 스키마 |

라벨은 제안이며 실제 GitHub에 생성되었음을 뜻하지 않는다. 우선순위는 `priority:mvp-core`, `priority:mvp-basic`을 제안하며, MVP 포함 여부와 순서는 팀이 명세를 확인해 결정한다. 하나의 작업이 여러 영역에 걸치면 관련 영역을 함께 표시한다.

## Issue 분리 기준

- 한 Issue는 담당자가 독립적으로 구현하고 결과를 확인할 수 있는 기능 또는 수정 단위로 나눈다. 위 표의 한 영역 전체를 하나의 Issue로 묶지 않는다.
- 예를 들어 재고 영역은 입출고 이벤트 기록, 이벤트 합산 조회, 실사 요청·정정, 발주 입고 대조로 나눌 수 있다.
- 발주 검토는 근거 수집, 검토 규칙, 승인·반려처럼 계약과 결과를 확인할 수 있는 범위로 나눈다. 여러 영역이 연결되는 작업은 선행 Issue와 연동 범위를 명시한다.
- Issue에는 작업 내용, 체크리스트, 검증 가능한 완료 기준과 관련 Notion 명세 링크를 기록한다. API 경로와 요청·응답은 구현 전 최신 명세에서 확인한다.

## 개발 시 지켜볼 경계

- 재고는 이벤트 합산으로 계산한다. 기존 이벤트를 수정·삭제하지 않고 정정 이벤트를 추가한다.
- 계산·판정·검증은 server의 규칙으로 수행한다. AI는 채팅 해석, 검토 의견서 문장, 엑셀 이관 제안, 부품 이름 임베딩에 사용하며 부품 매칭 순위는 매기지 않고, 실패 시 server의 대체 경로를 유지한다.
- 발주 검토는 직원 요청, 재고 부족, 놓친 발주 등 진입 경로를 구분하면서 공통 검토 규칙을 사용한다.
- 발주 수정 후 재검토, 입고와 기존 발주의 대조, 실제 납기 기록은 관련 Issue에서 명세와 함께 확인한다.
- API 계약, 권한·소유권, 실패 응답 및 중요 미검증 범위를 Issue와 PR에 기록한다. 수치·계산식과 확정되지 않은 세부 정책은 명세 확인 없이 확정하지 않는다.

## 브랜치 운영

병렬 개발을 시작할 때 `dev`를 통합 브랜치로 운영하는 방안을 제안한다. `dev` 생성 및 기준 커밋은 팀에서 정하며, 작업 브랜치는 Issue 번호를 포함한 저장소 규칙을 따른다. 작업 브랜치에서 `dev`로 PR을 열고 검증 후 병합하며, `dev`에서 `main`으로 반영한다. 브랜치 생성과 병합은 실제 저장소 상태와 승인 범위를 확인한 뒤 진행한다.

세부 Issue·브랜치·PR 작성 형식은 [협업 규칙](collaboration.md)을 따른다.
