## 결정과 근거

- **LLM 사용처는 정본 명세(`01`)를 따름(사용자 결정):** 채팅 해석, 엑셀 규격·카테고리 제안, 의견서 문장. 매칭 순위는 LLM 없이 규격 필터 + 임베딩·자모 유사도 + RRF로 정함. `CLAUDE.md`·`AGENTS.md`·`docs/work-areas.md`(dev)의 "별칭 후보 순위"는 따르지 않음. 공유 파일이라 해당 문구는 수정하지 않음
- **LLM과 임베딩 모두 Gemini API(사용자 결정):** API 키 하나로 둘 다 쓸 수 있고, 멀티모달이라 확장 기능(F-OCR 거래명세서 사진 입고)에도 같은 키를 쓸 수 있음
- **임베딩은 로컬 모델 대신 API로 계산(사용자 결정):** 명세 기술 스택의 "다국어 모델 (예: BGE-M3)"은 예시였으므로 Gemini 임베딩으로 대체
- **임베딩 호출은 `apps/ai`가 담당(이 기록에서 정함):** 키를 한 곳에서 관리하고 LLM 호출 지점을 `apps/ai`로 모은다는 `CLAUDE.md` 원칙과 맞춤. server와 계약을 정할 때 함께 확인
- 임베딩 실패 시 대체 경로(규격 필터 + 자모 유사도만 사용)는 명세에 없는 제안이라 규칙 문서에 "제안"으로 표시

## 남은 일·확인 필요

- **임베딩 차원:** `parts`의 임베딩 열 차원은 server의 DB 스키마와 맞춰야 함. 사용할 Gemini 임베딩 모델의 출력 차원과 pgvector 인덱스 차원 상한을 구현 전에 확인하고 server 담당과 합의 필요
- **모델 ID:** 채팅 해석·의견서용 Gemini 모델과 임베딩 모델 ID는 구현 시 최신 Gemini 문서로 확인
- **API 키 관리:** 환경 변수 이름, `compose.yaml`·`.env` 주입 방식 미정
- **의견서 검증 위치:** 숫자 검증과 재작성 반복을 server가 돌리고 ai는 문장만 쓰는지 확인 필요(앞선 기록 4번, 미해결)
- 다음 작업 후보: `packages/contracts`에 채팅 해석 요청·응답 스키마 초안 작성
