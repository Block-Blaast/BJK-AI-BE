# 부품 1,000종 nightly·채팅 매칭 성능 측정

- 날짜: 2026-11-05
- 영역: server
- 관련: Issue #100, 기능명세서 17장 비기능 요구사항

## 목적

- 배치 1,000종 5분, 채팅 응답 3초 기준을 실제 측정값으로 확인한다

## 측정 방법

- 명령: `make perf parts=1000` (`python -m bjk_server.seed.perf`). 개발 DB를 시연 시드(demo_v1)로 초기화한 뒤 합성 부품과 52주 출고 이력을 더한다.
- 합성 부품: 카테고리 4종 순환, 공급사 2곳 단가, 별칭 1개, 수요 유형 4가지(주별 출고 확률 0.9·0.4·0.2·0.7).
- nightly: `run_job`으로 외부 지표 → 근거 지표 → 장부 검증 전체를 앱 계정(RLS)으로 실행한 시간.
- 채팅: 해석 결과를 고정하고(LLM 제외) `handle_message`의 매칭·확인 카드 생성 시간. 20회, 기록은 롤백.
- 환경: Apple M4 로컬, docker compose `pgvector/pgvector:pg16`, 스택 `chore/perf-1000-parts/#100`(장부 검증·외부 충격 포함).

## 결과

| 부품 | 원장 행 | nightly | 채팅 중앙값 | 채팅 최대 |
| --- | --- | --- | --- | --- |
| 40 | 약 1,200 | 0.3초 | 3ms | 7ms |
| 1,000 | 29,334 | 4.0초 | 36ms | 38ms |
| 5,000 | 약 147,000 | 34.3초 | 192ms | 212ms |

- 1,000종 기준 nightly 4.0초(기준 5분), 채팅 36ms(기준 3초)로 두 기준 모두 충족.
- 채팅 매칭은 부품 수에 비례해 늘고(회사 전체 부품·별칭을 읽어 Python에서 점수 계산), nightly는 부품 수보다 빠르게 는다.

## 남은 점

- nightly의 숨은 재고 계산이 부품마다 전체 부품을 비교해 부품 수 제곱으로 는다. 5,000종에서도 34초라 지금은 두되, 부품이 수만 종이면 규격별 묶음으로 바꾼다.
- 채팅 측정은 LLM 호출 시간을 뺀 값이다. ai 연동 후 해석 지연(타임아웃 포함)을 더해 3초 기준을 다시 잰다.
- 원장 합산 재고는 1,000종에서 기준 안이라 `part_stock` 요약(명세 F-LEDGER-02)은 도입하지 않는다.
- 운영 서버 사양에서의 측정은 배포 환경 결정(#75) 후 한다.

## 함께 확인한 것: docker compose 기동

- `docker compose up -d --build`로 `db`·`server`·`scheduler`·`ai` 4개 서비스 기동 확인.
- 서버 컨테이너는 마이그레이션을 자동 적용하지 않는다. 새 볼륨이면 `make migrate`, `make seed` 전까지 `GET /api/v1/health`가 `db: error`.
- 마이그레이션 후 앱 계정(`bjk_app_login`)은 회사 지정 없이 부품 0건(RLS), 이메일 로그인·DEV-01 nightly 실행·부품 목록 정상.
